機械検出候補には、Bが「運送」と明かした後にAが「物流」と言い換えるような妥当な応答も含まれる。
候補を文脈付きで分類して実漏洩率を確定した後、再生成か除外かを決める。

ペルソナ先回りは次の二段階で効率的に検出する方針とする。

1. 居住地・職業・家族構成などの属性語と別表記を使い、Aが発話した時点までにBが対応事実を
   明示していない対話だけを高再現率で候補抽出する。
2. 候補についてのみ、Bのそれ以前の発話から自然に導ける応答か、内部ペルソナの先取りかを
   文脈判定する。確定した漏洩対話だけを保存済みmetadataから再生成し、同じ検査へ戻す。

機械候補をそのまま削除対象にはしない。言い換え（例: Bの「運送」に対するAの「物流」）や、
Bが子どもを明示した後の「お子さん」などを正常例として区別する。

`clean: false`は発生率が低いため、削除のみとし、件数補充のための再生成は行わない。

先取り確定対話は局所修正せず、同じペルソナ、blueprint、固定開始文、生成パラメータを保持して対話全体を再生成する。
seedだけを変更し、検出された属性について「B自身が会話で具体的に明かす前にAは使用しない」という注意を
生成プロンプトへ追加する。Bにその属性の開示を強制する必要はない。

再生成時の追加注意は地名・居住地だけに限定しない。検出されたペルソナ項目ごとに、居住地、職業、家族構成、
年齢、性別、経済状況、価値観、日常的な悩み、話題への乗り気度などを対象とする。複数項目が検出された場合は
すべての対象項目について注意を加える。個別注意に加え、「metadata内のBの全ペルソナはAの事前知識ではなく、
Bがそれまでの発話で具体的に明かした事実だけをAが使える」という共通規則も常に残す。

1. LLM判定で、問題のAターン、対象属性、判定、根拠となるBターン番号を構造化して保存する。
2. 初回判定が`leak`なら再生成を確定する。`grounded`なら維持する。
3. 初回判定が`uncertain`なら、初回の判定結果や理由を見せず、同じ会話prefixを別の判定プロンプトで
   独立に再判定する。再判定が`leak`なら再生成、`grounded`なら維持し、再び`uncertain`なら自動再生成せず
   要確認として残す。判定を無制限に繰り返さない。
4. 再生成対象は保存済みmetadataから生成条件を復元し、新seedで全対話を再生成する。
5. 通常品質ゲート、先取り候補抽出、LLM文脈判定を再実行し、全条件を通ったものだけ採用する。
6. 元dialogue/raw/metadata、判定結果、再生成プロンプト、旧新seed・試行回数を`provenance`へ保存し、
   採用時にmetadataとmanifestの件数・パス・再生成履歴を同期する。

LLM判定には未来のB発話を根拠として使わせない。候補Aターンまでの会話prefixだけを判定入力にし、
`leak`、`grounded`、`uncertain`の3値と、根拠となるBターン番号をJSONで出力させる。

## セッションをまたぐ運用ルール

リポジトリルートの`AGENTS.md`に、作業開始時の必読資料と、重要変更時にこのstatus文書を更新する規則を記載している。
エージェントは最初に`AGENTS.md`の指示へ従う。

重要な設定、品質判断、ジョブID、生成件数、出力先、再生成・移行作業は、その都度このファイルを更新する。
新しいセッションでは、作業開始前にREADMEとこのファイルを読み、現在の方針と成果物を確認する。
実装とMDの記載が食い違う場合は作業を進めず、実データとコードを検査して記録を同期する。
